# Runtime control: automatic execution with native creative gates

## Purpose and authority

The target is one continuous, recoverable production run from an idea to reviewed downloadable video. The user makes creative decisions only at the required native Question gates; every authorized technical operation between them proceeds automatically. Latest explicit user requirements govern over prior defaults, bundled style demo instructions and editing-reference examples. Read moodboard-visuals.md and story-development.md for the new research/direction → developed script → provisional shot script → actual character/scene/prop/board design and refinement handoffs. Explicit runtime/range remains binding through export; stage approvals retain precise versions. Core defaults remain Seedance 2.5, 16:9 unless explicitly overridden, model-BGM-free but AUDIBLE prepared shots, automatic final scoring unless excluded, same-scene continuity checks and hard-cut picture boundaries. Read `audio-postproduction.md` for sound planning, cleanup, audible QC and separate native editor tracks. Full source-style specifications remain authoritative for compatible artistic grammar, not for overriding these production constraints.

This is an orchestration contract, not executable tool syntax or an installed background service. Discover actual native schemas and use real node/asset/voice/editor handles. Do not print a fictional tool call or assign made-up field names to a provider payload. Apply the conceptual records below through supported notes/files/project metadata. If Question or another required capability is absent, identify that actual blocker; do not simulate success or invent an external fallback.

## Reconcile → act → observe → persist → repeat

At start/resume and after every tool result, callback or native answer:

1. Load the durable project and newest native editor state, refresh exposed tool bindings, and reconcile actual task statuses. Inspect any current input versions, user edits or outputs whose readiness changed. A saved callable name is not proof that it still exists after a context/tool change.
2. Apply returned decisions to the exact artifact/card/version they refer to. Ignore empty, ignored, default-selected or stale responses. Invalidate only real dependents of changed assets. A revised request authorizes its specified technical edits; do not ask an extra “continue” question.
3. Resolve the first unfinished required stage and its ready dependencies. If a required creative gate is pending, display its real artifact and issue/await that ONE native gate; script review first requires the full current screenplay saved/read back in actual canvas text/document node(s), with only a concise locating question and decision options in Question; keep it pending until a valid response. If the gate response is already recorded, do not ask it again. Do not submit a duplicate copy of a card that is already awaiting a response.
4. Otherwise select the next permitted real action: perform real research or development, create a missing shot script/scene/board, refine a diagnosed image defect, create a missing script/asset, resolve an input, submit a ready job, inspect a completed result, normalize shot BGM, prepare a preview, modify the native draft, export an approved revision, or verify an actual download. Independent jobs can progress while another waits/fails; a dependent job cannot borrow an unrelated ready asset.
5. Persist the job/request key and intended action before dispatch, then persist actual returned IDs/status/results and the next action. If the tool returns pending, register the actual supported continuation/callback or query the same task until terminal. Observe service quotas/backoff, with at most the existing bounded correction/resubmission rules. Query ambiguous accepted work before retrying to avoid duplicate paid calls. Do not use repeated generation as polling.
6. Inspect actual outputs and record checks separately from user approval. Advance the stage only when its stated exit conditions are true, then immediately repeat this loop. A progress note such as “next I will generate” does not execute the next action. Do not end the resumed turn at that note while a ready authorized action remains.

Only return control intentionally for a real native decision, explicit pause/cancellation, a saved unrecoverable blocker, or completed delivery. Host-imposed turn termination needs a real durable host continuation to resume automatically. Store its handle and next action; if absent, honestly report the capability limit once. Text instructions cannot guarantee an agent wakes itself up. Do not ask the user to type “continue” as the routine job scheduler.

## States and evidence

Keep these distinct: PLANNED, INPUTS_READY, SUBMITTED, RUNNING, GENERATED, QC_READY, USER_APPROVED, BLOCKED and FAILED. Use equivalent actual host values where applicable; these labels are not invented API arguments.

- INPUTS_READY: required text/handles resolve in this project/session, producer tasks are ready, owners/versions match and current operation constraints pass. Omit absent optional inputs; never supply empty reference objects or substitute node/task IDs for content handles.
- GENERATED: this exact task returned a successful accessible output, not merely an ID or global success toast.
- QC_READY for a shot: its actual prepared model-BGM-free video resolves and plays with ALL expected speech/narration, effects and ambience audible, except justified intentional-silence intervals. Verify the sound plan against actual synchronized playback, not merely audio-stream presence. Measured ratio/duration, identity/voice/wording, timing/lips, scene/mode and source-prefix trim pass. A mute intermediate, detached audio or sound promised for later cannot pass. Store raw output, cleanup/composition IDs, audible evidence and prepared output separately.
- SCRIPT_REVIEW_READY (conceptual, not an API enum): the full current screenplay is actually saved in readable canvas text/document node(s) and read back complete. Store real document handles, content version and save/readback evidence; a chat draft, placeholder node or screenplay pasted into Question is not review-ready. Reconcile/resume the existing script write before issuing its decision-only card.
- USER_APPROVED: an actual positive native answer for that artifact/version. One approved clip, an approved table or generation success does not approve all shots.
- DELIVERY_READY: every required current shot is approved, post-scope is answered, selected editing is performed in native Video Editor, current preview revision is approved, and that revision has a verified downloadable export matching the approved scope. Explicit no-edit clip delivery is separately labeled and never called a stitched movie.

For each dispatch store project/stage/logical-artifact/version, input fingerprint, real node/task IDs and current state. Use actual provider idempotency support if exposed. A local request key helps locate existing work; it is not itself proof the provider deduplicates. A task with an unknown submission result must be reconciled before another billable submission.

For all native audio, `speech-inputs.md` is a mandatory BEFORE-EXECUTE preparation/readiness contract, not just an error appendix. Validate operation-specific real inputs and save their observed versions. On an unresolved empty-content failure, hold unsubmitted jobs sharing the faulty input path rather than executing every role or the whole canvas; continue only genuinely unaffected ready work that does not cross the same barrier. A changed node name, mere delay or serial scheduling is not a repaired input. Resume the held queue after actual repair and successful repaired deliverable; retain the same logical-job retry budget and actual acceptance checks.

## Canvas synchronization, existing nodes and submission recovery

### Separate node setup, accepted jobs and outputs

A Canvas tool call marked Completed, a task checklist marked 8/8, or a visible image/audio/video node does NOT prove media generation ran. Such a call may have created nodes only. Maintain three distinct records for each logical asset/version: node preparation (actual node and saved prompt/inputs), generation acceptance (actual task or authoritative acceptance evidence), and output (actual ready media handle). Never use node setup success to complete a production stage.

Track node existence, input-save/readback result, canvas revision/sync result where exposed, submission certainty, task/output IDs, observed status, attempts and next action. Distinguish these conceptual conditions without inventing provider enum fields:

| Observation | Meaning and next action |
|---|---|
| Node created, no accepted task and no output | Preparation only; resolve/save inputs, synchronize as supported, then submit when acceptance is known absent |
| Authoritative tool result explicitly says no new task was submitted | NOT_ACCEPTED for that attempt only; preserve existing nodes, repair/reconcile sync, then submit once it is safe |
| Timeout/sync error with unclear acceptance | ACCEPTANCE_UNKNOWN; inspect original task/node/history through real supported reads; do not resubmit just because an ID is missing |
| Task accepted/queued/running | Observe that same task; do not start another generation to recover a canvas display |
| Successful media exists but canvas attachment/display is stale | Rebind/register the verified existing output through supported native operations; do not regenerate it |
| Persistent synchronization failure with no safe inspection/repair | Save precise evidence and resume point; native recovery/host support is needed, not a duplicate canvas |

Only the actual tool result/current provider state establishes NOT_ACCEPTED. An earlier assistant message saying “system confirms no new task” is not independent evidence. Absence from one eventually consistent listing is not conclusive non-acceptance. Bind the observation to its exact dispatch/version, since an older attempt may still have been accepted. If the tool exposes neither a task ID nor authoritative status, leave acceptance unknown rather than guessing.

### Start production with the first real required asset

After script approval, reuse matching existing character/prop nodes and actual ready images. Create/configure the first missing required character sheet (or real required scene/important-prop image when no character sheet is required), read back its saved prompt, image operation, 16:9 setting and necessary real references where supported, and submit that REAL asset. Observe its task/output end to end before expanding the queue. This is the user's first deliverable, not an extra paid probe. Prefer a serial automatic queue for remaining required character/scene/prop jobs until the route is healthy; increase concurrency only within actual quotas and dependencies. An atomic create/configure/execute tool may do this in one call; do not invent separate save/sync endpoints.

First create the provisional shot script under story-development.md, then extract the FULL cast using characters-voices.md, scene/set states and required boards using moodboard-visuals.md, AND important objects using props-assets.md from the exact approved script. The first-asset rule controls internal dispatch only, not asset scope/user gates. Do not ask for role/prop lists, supplied images, manual nodes or per-item approval. On a ready output, automatically process the next required asset. Once all initial current character/scene/prop master images pass inspection, show all real initial character/scene/prop masters at the applicable combined visual gate under moodboard-visuals.md (legacy no-scene titles under props-assets.md), then proceed to voices. Props remain separate identities from the cast. Temporary recovery does not authorize skipping a required object/role or starting dependent work before approval; preserve genuine unrelated approvals on resume.

Do not create an entire empty-node batch and mistake it for production. If a batch already exists, enumerate it through actual native reads and map logical role IDs to their existing node IDs/input versions. Preserve each node, approved script and successful media. Finish its missing prompt/settings/inputs and submit the first eligible unaccepted node when safe; continue the remaining existing nodes automatically. Do not blindly recreate, delete, or rename the batch to reset error counters. Replace one node only if current evidence shows it is unusable, the native tool supports replacement, and acceptance/dependencies have been resolved.

Serialize mutations of a shared canvas/project: only one actual save/create/connect/execute mutation may be in flight through that coordinator. A pending save/revision/registration is reconciled before a dependent submit. Independent provider jobs may run concurrently where supported after their inputs are committed; this does not authorize overlapping stale canvas writes. Read latest state before each write and honor actual revision/lease fields if exposed. Do not overwrite concurrent human edits or run a broad whole-canvas execute merely to probe one node.

### Bounded recovery for pre-execution synchronization failures

Treat “pre-execution synchronization failed / synchronization of existing task results failed” as its own orchestration phase. It does not by itself mean the image/video model failed, the prompt was rejected, the script needs rewriting, a copyright block occurred, or the platform is globally unavailable. Screenshots containing only the agent's description do not expose the underlying error; inspect the relevant raw native tool result when available.

1. Record the actual failing operation, phase, affected project/revision/node, exact error/request/log IDs, any task IDs, acceptance certainty and last successful checkpoint. Stop dependent billable submits while acceptance/sync is unresolved. Avoid new image/audio/video execution calls just to test connectivity.
2. Inspect supported read-only task/node/output state, scoped to the affected work and any explicitly reported stale earlier task. Some Canvas calls combine status sync with execution: inspect the real schema/result before assuming a call is read-only. Use actual status/list/read/reconcile/refresh capabilities only when exposed. A tool label or this document cannot create a repair API.
3. For a transient read/sync failure, allow at most THREE additional non-generating reconciliation attempts in that recovery episode, honoring Retry-After and real host waits/backoff (for example 1s, 3s, 8s if no service guidance exists). Persist the budget across turns and callbacks; do not reset it by changing nodes, rereading the Skill or renaming the phase. A scheduled attempt counts only when the host actually executes it. Normal observation of a healthy running job is not a failed-sync retry.
4. If an old accepted task has completed, recover its actual output/attachment and record it; if still running, track the same job with actual host continuation. If the native response identifies a repairable stale binding/revision, perform only the supported scoped refresh/rebind after inspecting current state. Do not clear histories, delete old tasks, detach unrelated media, cancel paid work, force a stale revision or bypass a required global sync barrier.
5. After synchronization really succeeds, re-read acceptance for ALL previous attempts. For authoritative NOT_ACCEPTED with ready saved inputs and no other accepted/unknown attempt, submit the existing node once within the separate generation-submission budget. For accepted work, continue its original task; for successful work, reuse its output; for unknown acceptance, keep reconciling within the remaining safe budget and never duplicate paid work. Re-enter the normal automatic loop immediately after recovery; no “type continue” checkpoint.
6. If the budget is exhausted, there is no supported safe repair/status route, or the actual error is non-transient, preserve a real blocker. Continue independent work only if it does not cross the failed shared sync barrier. Do not keep sending the same failing Canvas execute or claim indefinite automatic recovery. Register a delayed resume only if the host actually offers it, saving its real handle. Otherwise report that automatic resumption is unavailable, not “I will retry later” without a scheduled operation.

Reconciliation attempts do not consume or increase the existing maximum TWO generation resubmissions for confirmed transient submission failure. A submission whose acceptance is unknown has zero safe automatic resubmissions until resolved. Deterministic input errors and policy rejections retain their separate rules in production-requests.md. Any recovery budget is per unresolved episode/dispatch, not an unlimited allowance per node.

### Progress, recovery card and resume

Maintain counts independently: nodes prepared / tasks accepted / outputs generated / QC-passed / user-approved. When only placeholders exist, report e.g. “节点已准备 N/N；图片生成 0/N，尚未提交或提交待核实”, never “角色完成” or overall production complete. If the host checklist cannot express all states, name setup versus generation as separate tasks and use an actual persistent status note; do not fabricate a counter API.

At a true blocked barrier, use the actual native Question card with concise supported choices such as “重新检查并恢复 / 保存并暂停 / 查看故障详情”, respecting its real option limit and built-in Other. Explain what is known, unknown and still pending. The recheck choice authorizes a new bounded READ/RECONCILIATION episode, not blind media resubmission or resetting unknown acceptance. A persistent platform failure may require host support; do not automatically contact anyone. If the native card/state write is itself unavailable, provide an honest saved blocker report through the available channel instead of inventing a card or claiming it was saved remotely. Do not turn every temporary retry into a user question.

On later resume, refresh actual bindings and reconcile saved nodes/tasks/outputs first, preserve genuine existing approvals, then run only missing ready work. A prose “script confirmed” note without the actual native response/version does not supply approval. Do not restart the script/style interview or recreate successful characters as a workaround. Save the precise next eligible node/action and any verified unresolved task/log IDs, so neither the user nor the agent must reconstruct the failed stage from chat history.

## Dependency rules that prevent unnecessary stops

**Two approval levels for extension:** table approval authorizes producing its planned same-scene chain. A successor may consume a QC_READY prepared predecessor from that chain before per-shot user review, provided all foundational script/character/voice approvals are valid. Do not wait for the later USER_APPROVED shot flag to produce that already authorized successor: that would deadlock “generate all, then review each.” User approval of EVERY current prepared shot is still mandatory before post-production. A predecessor revision invalidates its affected extensions and approvals; recompute only those descendants.

**BGM cleanup before post-choice:** native shot-audio cleanup is authorized technical preparation. Remove ONLY background score; retain/restore exact speech, required effects and ambience through a supported native route and verify an actually audible prepared shot BEFORE its card. Only released successful outputs may be processed; policy-blocked results remain blocked. A full-mix mute stays intermediate until all required sound is composed and checked. This does not authorize stitching/captions early. Later automatically fitted original/cleared final music is a separate editor track and is included in final preview approval; honor explicit no-music scope.

**Scoped invalidation:** a different role voice affects that role's auditions/speech and dependent speaking shots, not silent unrelated shots. A ratio change affects boards, affected clips, extensions and edit layout; a fixed 16:9 character turnaround need not be regenerated if its identity remains correct. A music-only final edit does not invalidate the script/character approvals. Substantive new words, identity, voice or story changes revisit the relevant native gates; technical re-encoding/handle repair preserving content does not.

**Production table versus edit timeline:** retain the approved source production table/version and speech assets. Save native editing placements, trims, beat markers and caption cues in a separate versioned edit map, linked to their source shot/span. An authorized handle trim, hard-cut adjustment or music alignment can change final placement without silently overwriting the approved source table or demanding whole-film regeneration. Recompute final duration/caption offsets and present the new edit revision at final review. If approved dialogue/action is lost or reordered substantively, obtain the appropriate creative revision rather than calling it a timing fix.

**Source and instance coverage:** every required approved shot/line span must be represented in the final selected scope, with no accidental repeated extension prefix. Multiple non-overlapping instances of one source file can be legitimate; count content coverage rather than raw file-instance count. Mark deliberate reuse only when actually requested/approved. Dialogue/narrator dry audio, source sound, model BGM and final project music have distinct roles.

**Caption scope:** subtitle choice controls dialogue captions. It does not remove approved story titles, environmental writing, evidence labels or style-required data typography. Keep such text roles explicit. Do not bake dialogue captions into generated video by default; use editable native captions when selected, disable unwanted automatic captions and check for duplicate burnt-in text. A caption-only request preserves existing approved assembly or captions individual approved clips, without silently stitching them.

## Native decisions without questionnaire churn

Creative gates are researched mood-board/keyword direction (or real library choice), script, ONE applicable character/scene/important-prop master review, role voices/auditions, final master table WITH all real refined-or-inspected-pass shot boards, EVERY current video shot, post-scope and final edit/revision review. Internal development/shot-script drafting and routine defect correction auto-advance; no extra questionnaires. Existing approvals survive resume when still valid. Use moodboard-visuals.md's scene-inclusive title or props-assets.md's applicable legacy title for ONE combined initial visual review, not extra prop-list/per-object questions. Newly discovered required props get an incremental native review before their affected table/shots without restarting unrelated work. Show real artifacts first. Start from the idea without an initial serial questionnaire; reuse genuine supplied decisions/approvals. Skip only inapplicable stages with a reason, never required props just because no cast exists; no fake narrator portraits or silent-role auditions. No required scene/board is skipped merely because no cast exists; an explicitly approved existing design can be reused. Pending direction or table/board approval blocks its dependent paid production; real image refinement does not reset retry budgets. Store research sources/metric evidence, keywords/direction, screenplay development, provisional shot plan, scene maps, board/edit lineage and linked approvals alongside existing media state.

Fit the actual Question schema's option/question limits. Post-scope has three explicit normal routes plus native Other when provided. Other is not a duplicate fake option. Each voice option is a complete meaningful profile. A batch of shot questions preserves an individual shot/version decision for every displayed clip. Large preview collections are paged without approving unseen items.

Continue-modifying opens native card text/Other asking the target shot/time/track, the issue and desired change. Capture real nonempty instructions, apply them to the SAME editor draft, preserve unrelated user locks/overrides, update dependent sound/captions, and return a new actual preview/version to final review. Do not request main-chat typing or treat a click on “modify” as a full edit instruction. Ambiguity gets one focused native clarification, not a general new briefing interview. Missing native text entry is a precise host blocker.

## Failure isolation and final delivery

Route input-ID/readiness errors, invalid parameters, transient failures and policy rejections separately using production-requests.md. Never spend a retry allowance for one error class on another. Preserve exact error/stage/task/role/shot evidence; do not assert a hidden root cause. Continue independent ready jobs; at a true dependency barrier present one native recovery card for actual unresolved decisions. Repeated notifications of one terminal task are one failure. No hidden omission, unheard approval or fabricated success to finish a checklist.

Final confirmation approves the displayed current edit revision and authorizes its native export. Re-read the draft immediately before export; changed drafts return to review. Wait for actual export success, verify output/ratio/duration/coverage, complete dialogue and sync, selected caption state, hard cuts, intended final music and real download access. A cloud draft or expired/guessed URL is not downloadable media. Refresh through native support when available. Deliver the actual download with real editable draft/subtitle references when supported, and retain the project state for later revisions. Do not publish generated media outside the requested destination.
